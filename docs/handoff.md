## 완료된 작업

### 북마크 일괄 폴더 이동 — 모달 방식으로 재설계 (2026-07-27)

**1차 설계(액션 행 `선택` 토글 + 행 체크박스)는 폐기했다.** 사용자 지적 2건:
1. **UI 깨짐** — 액션 행에 버튼이 하나 더 늘자 384px 폭을 넘겨 "선택" 글자가 세로로 쪼개졌다. 직접 원인은 `.ba-select-toggle`을 **공용 버튼 스타일 선택자 목록에 안 넣어** 브라우저 기본 버튼으로 렌더된 것(폰트·nowrap·패딩 없음). 액션 행에 `flex-wrap`도 없었다
2. **라벨 모호** — "선택"만으로는 무엇을 위한 선택인지 안 드러난다

**최종: 기존 카드 액션 `⋯ → 다른 폴더로 이동`이 여러 개 선택 모달을 연다.** 진입점이 이미 이름으로 목적을 말하고 있어 라벨 문제가 사라지고, 액션 행에 버튼을 늘리지 않아 폭 문제도 사라진다.
- `showFolderPick(current, title, multi)` 확장 — `multi`가 오면 **옮길 북마크 목록**(체크박스 + 현재 폴더 표시 + 전체/해제 + N개 선택)을 폴더 칩 위에 함께 띄운다. 누른 북마크는 **미리 체크**되어 하나만 옮길 때도 흐름이 같다
- 목록 재렌더는 목록 영역만 — 폴더 칩 선택 상태가 흔들리지 않는다. 0개 선택이면 `이동` 버튼 비활성
- 이동은 `moveBookmarks`(한 번의 저장소 쓰기, 상대 순서 유지) 그대로 사용
- 1차 설계의 `selectMode`·행 체크박스·액션 행 토글·관련 CSS는 **전량 제거**(잔재 0건 확인). `bulkMove.dom.test.js`(선택 모드 DOM 테스트 11건)도 대상이 사라져 삭제 — **모달은 panel.js 소속이라 자동 테스트 밖**이고 store 계층(`moveBookmarks` 5건)만 남는다

### (폐기된 1차 설계 기록) 북마크 일괄 폴더 이동 (2026-07-27, 사용자 제보)

**증상**: 북마크를 폴더로 정리할 때 하나씩 ⋯ → 이동을 반복해야 해서 부담이 크다.

- `store.js` `moveBookmarks(ids, folderId)` — 여러 개를 **한 번의 저장소 쓰기**로 이동(하나씩 부르면 읽기·쓰기가 반복되고 중간 상태가 노출된다). 대상 폴더 맨 뒤에 붙이되 **서로의 상대 순서는 유지**. 히스토리·없는 id는 무시하고 실제 옮긴 개수만 반환
- `renderList.js` **선택 모드** — 액션 행의 `선택` 토글로 켠다. 평소엔 체크박스를 숨겨 카드가 복잡해지지 않게 하고(드래그 손잡이 자리를 그대로 씀 → 레이아웃 흔들림 없음), 모드일 때만 노출
- 선택 바: `N개 선택 · 전체 선택 · 해제 · 폴더로 이동`. 폴더 선택은 기존 `showFolderPick` 재사용(신규 다이얼로그 0)
- **체크 시 재렌더하지 않는다** — 재렌더하면 스크롤이 맨 위로 튀어 연속 선택이 불가능해진다. 체크박스·행 강조·개수만 직접 갱신
- 선택 중에는 이름을 눌러도 검색이 열리지 않고 선택만 토글(오클릭으로 페이지가 떠나는 것 방지)
- 이동 완료 시 선택 모드 자동 해제 + `N개를 옮겼습니다` 토스트. 폴더 선택 취소 시 선택 상태 유지

**테스트가 잡은 버그 1건**: 선택 모드에서 북마크가 0개가 되면 토글 버튼은 사라지는데 **선택 바만 남아 빠져나갈 방법이 없었다.** 바를 `bookmarks.length`가 있을 때만 렌더하도록 수정.

**테스트 노트**: `selectMode`는 모듈 레벨 상태라 테스트 간에 남아 순서 의존이 생겼다(제품은 페이지 로드마다 초기화되므로 문제 없음). 테스트 헬퍼에서 리스너를 매번 떼고 선택 모드를 꺼진 상태로 정규화해 해결.

테스트 **298/298**(신규 16: `store` 5 + `bulkMove.dom` 11).

### 조건 칩 클릭으로 능력치 추가 + 빈 폴더 표시 (2026-07-27)

**① 조건 칩 클릭 → 그 검색의 능력치만 지금 검색에 추가** (사용자 제안)
조건 묶음(칩 줄)은 "등록 → 이름 → 클릭" 3단계라 자주 쓰는 소수에만 맞는다. 북마크·히스토리 카드의 **조건 칩을 직접 클릭**하면 등록 없이 그 능력치를 바로 얹는다 — 사용자 계정의 raw query 보유 레코드 68개가 즉시 재료가 된다.
- 조건 칩은 원래 클릭 동작이 없어(호버 툴팁 전용) 충돌 없음. 툴팁에 "클릭하면 이 능력치를 지금 검색에 추가" 한 줄 추가, `cursor: pointer` + hover 강조
- **유형(아이템 종류)은 일부러 제외** — 보던 검색의 유형을 덮으면 '얹기'가 아니라 '바꾸기'가 된다. (칩 줄의 조건 묶음은 완성형 의도라 유형 포함 유지)
- **매번 레코드의 원본 query를 새로 읽는다** → 저장 스냅샷이 아니라서 "옛 묶음엔 그룹이 없다" 같은 마이그레이션 문제가 원천적으로 없다
- `applyAndGo()`로 실행 경로를 공통화(칩 줄·조건 칩이 같은 병합·POST·토스트·연타 차단을 공유)
- raw query가 없거나 능력치가 0개인 레코드는 클릭 불가(클래스 미부여)

**② 폴더 추가가 안 되던 문제** (사용자 제보)
`renderList`가 **빈 폴더를 전부 건너뛰고 있었다**(`if (!items.length && !(isCurrent && g.id === null)) continue`). 새로 만든 폴더는 당연히 비어 있으므로 **만들어도 화면에 안 나타나고**, 드래그해 넣을 대상조차 없어 폴더 기능을 시작할 수가 없었다. 저장은 정상이었고 렌더만의 문제.
- 현재 리그 섹션은 **빈 폴더도 표시**(드롭 타깃 "여기로 드래그"까지). 현재가 아닌 리그 섹션은 기존대로 숨김 — 조작 대상이 아니고 목록만 길어진다

### 조건 묶음 — 능력치 그룹 보존 (2026-07-27, 사용자 제보)

**증상**: '숫자(count)' 그룹으로 나눠 만든 검색을 조건 묶음으로 등록하면 그룹이 저장되지 않는다.

**심각도가 보이는 것보다 높다 — 검색 의미가 바뀐다**: `count` 그룹은 "이 중 N개만 만족하면 됨"이다. 평탄화해 `and` 하나로 합치면 **전부 만족해야 하는** 완전히 다른(훨씬 좁은) 검색이 된다. 단순 누락이 아니라 조용한 오작동.

- `conditionSet.js` — `extractConditionSet`이 `groups: [{type, value, filters}]`를 함께 반환(그룹 타입 + 그룹 값 `숫자 ≥N` + `weight` 값까지 보존). 평탄 `stats`는 칩 개수 표시·하위호환용으로 유지
- `mergeConditionSet` 병합 규칙을 그룹 타입별로 분기:
  - `and` → 현재 검색의 `and` 그룹에 얹기(중복 id는 갱신). "전부 만족"이라 합쳐도 의미가 같다
  - `count`·`weight` 등 → **통째로 새 그룹으로 추가**. 그룹 자체가 하나의 조건이라 합치면 깨진다
- `store.js` — `addConditionSet`이 `groups`를 실제로 보관(안 그러면 추출해도 저장 단계에서 버려짐)
- 하위호환: `groups` 없는 기존 묶음은 `stats`를 `and` 그룹 하나로 취급

**검증**: 테스트 **273/273**. 스크린샷 시나리오(숫자≥1 그룹 + 숫자≥2 그룹)를 픽스처로 고정 — 그룹 2개가 `and`로 합쳐지지 않고 각자 `value.min`까지 유지되는지, 현재 검색의 기존 그룹은 안 건드리는지 확인.
**라이브 검증 (2026-07-27)**: 그룹 나뉜 북마크("목걸이 - 초반")를 새로 등록 → 얹기 → 필터 UI에 `숫자 (1)`·`숫자 (2)` 그룹이 각자 값과 소속 조건까지 그대로 재현됨(스크린샷 확인).

**라이브에서 이어서 발견 — 같은 그룹 중복 추가**: 이미 그 그룹을 가진 검색에 얹으면 동일한 `숫자 1` 그룹이 두 개가 됐다. `and`는 stat id로 중복을 걸렀지만 `count`·`weight`는 무조건 append했기 때문. `groupKey()`(타입 + 그룹 값 + 조건 집합, 순서 무관)로 동일 그룹이면 건너뛴다. 같은 묶음을 두 번 얹어도 그룹이 안 늘어난다. 비활성 그룹과는 비교하지 않음(검색에 적용 안 되므로).
**라이브 확인 완료(2026-07-27)**: 같은 조건을 두 번 얹어도 그룹 블록 수 4개 → 4개로 동일. **URL 해시조차 그대로**(`aL5PGwvMSe`)였는데, 병합 결과가 완전히 같아 거래소가 같은 검색을 돌려준 것 — 멱등성의 직접 증거.


### 환산 칩 — 큐레이션 밖 화폐까지 확장 (2026-07-27)

**원인 — 조용한 회귀**: 경제 API `items`의 키가 **Metadata 경로**(`Metadata/Items/Currency/...`)인데 `itemsRate()`는 거래소 화폐 id(`chrome`)로 조회하고 있었다. 실측 결과 818개 키 중 짧은 id는 **0개** — 이 폴백은 **한 번도 매칭되지 않았다**. 즉 환산 칩은 큐레이션 4종(엑잘·디바인·미러)에서만 동작했고 나머지는 전부 조용히 빠져 있었다. 핸드오프의 "63개 화폐 커버"(2026-07-04) 기록은 BE 스키마 변경 이후 **낡은 정보**였다.
**게다가 기존 테스트가 짧은 키 형태(`{chrome:{...}}`)를 가정하고 있어 프로덕션이 깨진 채로 계속 green이었다** — 픽스처가 실제 응답과 어긋나면 테스트가 회귀를 못 잡는다는 사례.

**수정 — 한글 이름으로 조인**: 두 데이터를 잇는 유일한 공통 키가 한글명이다(거래소 static API의 화폐 `text` == 경제 API의 `ko_name`).
- `currencyRates.js` — `indexItemsByName(items)` 신설(ko_name 색인, 818개 전부 보유·**중복 0** 실측). `itemsRate(index, name, base)`로 시그니처 변경. 색인은 rates 응답당 1회만(WeakMap 캐시 — 800+ 항목을 결과 행마다 훑지 않게)
- `content-main.js` — `ensureCurIcon` → `ensureCurrencyStatic`으로 확장: 기본 화폐 아이콘 + **화폐 id→한글명 맵**을 한 번에 만든다(이미 부르던 API라 요청 추가 없음). `baseFromPrice(..., curNames)`로 전달
- 이름 맵 로드 전에는 기존 큐레이션 4종으로 폴백 → 회귀 없음

### 아이템 검색칸 완전 삭제 불가 버그 수정 (2026-07-22, `c58e200`에 포함·푸시 완료)

**증상(사용자 제보)**: 거래소 "아이템 검색"(Alt+F) 입력칸에 이미 검색어가 있을 때, Backspace·Ctrl+A+Delete 등 무엇으로 지워도 검색어가 지워지지 않는다.

**원인**: 우리 확장의 `fuzzyPrefix.js`(퍼지 검색 기본화를 위해 검색칸 맨 앞에 "~"를 항상 유지·자동 복구하는 로직)가 지나치게 공격적이었다 — ① `input` 리스너가 값이 빈 문자열이 되는 즉시 "~"를 다시 채워 넣고 ② `keydown` 가드가 "~" 한 글자만 남았을 때도 Backspace를 막아, **어떤 방법으로도 검색칸을 진짜로 비울 수 없었다**(최소 "~" 하나는 항상 남음). Alt+F 단축키 자체의 문제는 아니고, 페이지에 상시 주입되는 이 안전망 로직이 원인.

### 리그 이관(저장 조건 → 현재 리그 재검색) + 가이드 투어 예시 요소 (2026-07-22, `develop` 푸시 완료)

**핵심 판단 — 미완료 6번의 전제 교정**: "자동 채움 = 거래소 Vue 필터 UI를 클릭·타이핑으로 흉내내야 함(고리스크)"라는 기존 전제가 틀렸다. `cross-site-receiver.js`가 이미 쓰던 **공식 검색 생성 API**(`POST /api/trade2/search/poe2/<리그>`)에 저장된 raw query를 그대로 다시 제출하면, 반환된 해시 URL로 이동하는 것만으로 거래소가 **필터 UI까지 조건대로 채워** 렌더한다. UI 자동화 없이 (a)안이 노리던 결과를 그대로 얻는다. 유일한 걸림돌은 "raw query를 저장하지 않았다"였고, 그건 필드 추가로 해결.

- `src/lib/tradeSearch.js` **신규** — 순수 헬퍼 4종. `searchApiPath`/`searchResultPath`(게임별 경로·리그 인코딩), `isSafeSearchId`(응답 id를 URL에 이어 붙이므로 `[A-Za-z0-9_-]{1,64}`만 허용 — 경로 탈출 차단), `sanitizeQuery`(최상위 키를 query·sort로 화이트리스트 + 20KB 상한 + JSON 왕복). 헤더에 "왜 UI 자동 채움이 아닌가" 근거 기록
- `store.js` — 레코드에 `query`(raw 검색 조건) 추가. `backfillQuery(dedupeKey, game, query)`: query 도입 전 저장한 **구 북마크는 사용자가 같은 조건을 재검색하는 순간 자동으로 채워져** 이관 가능해짐(있는 값은 안 덮음). `migrateBookmarkLeague(id, url, league)`: url·league·lastUsedAt만 교체(이름·폴더·순서·메모·id·query 보존). `overwriteBookmark`·`markUsedByUrl`도 query 승계. `importBookmarksJSON`은 남의 query를 `sanitizeQuery` 통과시킨 뒤에만 채택(불합격이면 조건만 버리고 북마크는 유지)
- `content-main.js` — 히스토리 저장 시 `query` 동봉 + `backfillQuery` 호출. `migrateSearch(query, league)`: same-origin POST → 429/401·403/기타 HTTP를 각각 다른 사유로 반환 → id·URL 검증 후 결과 URL 반환. **일괄 이관은 의도적으로 미제공**(요청 폭주 시 GGG rate limit에 걸리면 거래소 검색 자체가 막힘)
- `renderList.js` — 진입점 2개: ① **지난 리그 북마크 이름 클릭 시 제안 팝오버**(기존 `showConflict` 재사용 — 신규 UI 요소 0): 조건이 있으면 [그대로 열기 / 현재 리그로 다시 검색], 없으면 **저장된 조건 요약을 보여주고** [그대로 열기](= 검토했던 "참고용 재구성 도우미"안의 가치를 여기서 흡수, 110자 초과 시 말줄임) ② ⋯ 팝오버의 `현재 리그로 다시 검색`(에메랄드 `.ba-act.relg`, query 있는 북마크만 노출 — 현재 리그 북마크도 해시 만료 복구용으로 사용 가능).
