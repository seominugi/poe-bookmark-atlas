# poe-bookmark-atlas 핸드오프

POE2 거래소(poe.kakaogames.com) 북마크·히스토리 관리 Chrome MV3 확장 (Vite + @crxjs/vite-plugin). 우측 도킹 Shadow DOM 패널. 제작 브랜드: 서미누기.

## 찜 상태가 오래되면 먼저 말을 건다 — 자동 주기 대신 (2026-09-05)

**사용자 결정**: ④-b(갱신 간격 자동 주기)를 **거절 확정**하고, 내가 권고한 **대안**을 채택했다.
*"대안으로 가자 — 확인할까요 버튼."*

자동 주기의 값어치 대부분은 **잊지 않고 갱신되는 것**인데, 그건 "지금 오래됐다"고 알려 주기만 해도
얻어진다. 그러면서 「기능 수용 기준」의 *백그라운드 상시 동작*에는 걸리지 않는다 — 사용자가 눌러야
돌고, 안 돌면 그 자리에서 보인다. **새 권한 0 · 새 타이머 0.**

### 한 것

- **`watchNudge()`**(`src/lib/watchRefresh.js`) — 순수 판정 함수. 오래된 찜 수를 세고 띄울지 정한다.
- **찜 섹션에 `.ba-wnudge` 배너** — *"🕐 찜 **3개**를 확인한 지 오래됐어요 · [지금 확인] · ✕"*.

| 규칙 | 값 | 왜 |
|---|---|---|
| '오래됨' 기준 | **1시간** (`WATCH_STALE_MS`) | 매물은 분~시간 단위로 팔린다. 하루는 너무 길고 몇 분은 같은 세션에서 계속 뜬다. ⚠ **측정값이 아니라 고른 값이다** |
| 띄우는 최소 개수 | **2개** | 하나뿐이면 행의 개별 '확인' 으로 충분하다. 한 건 때문에 배너를 띄우면 배너가 목록보다 커 보인다 |
| 확인한 적 없음 | **오래된 것으로 센다** | 그게 가장 모르는 상태다 |
| `✕` | **24시간 스누즈** (`uiWatchNudgeSnooze`) | **영구 숨김은 두지 않는다** — 한 번 잘못 누르면 기능이 영영 사라지는데 사용자는 되돌릴 방법을 못 찾는다 |

### 배선에서 조심한 것 — 뒤집기 전에 읽을 것

- **`지금 확인` 은 배너를 먼저 지우고 순회를 시작한다.** 안 지우면 도는 중에 다시 눌러 **'중단'** 이
  된다 — 누른 것과 정반대 결과다. 진행 표시는 섹션 머리의 '전체 확인' 버튼이 이미 나르므로 거기 위임한다.
- **도는 중에는 배너를 그리지 않는다.** 지금 갱신되고 있는데 "오래됐다"고 말하면 어긋난다.
- **`✕` 는 재렌더하지 않는다.** 배너 하나 지우려고 목록 전체를 다시 그리면 스크롤이 튄다.
- **배너는 `.ba-wnudge` 가 `flex-wrap: wrap`** 이다. 문구+버튼+✕ 가 최소폭(가용 342px)에 빠듯한데,
  nowrap 이면 넘쳐 잘린다. wrap 이면 버튼이 아랫줄로 내려갈 뿐 아무것도 안 잃는다.

### 검증 — ⚠ **화면 실측을 안 했다**

사용자가 **방송 중이라 E2E(브라우저 하네스)를 하지 말라고 지시**했다(2026-09-05). 그래서 이번 변경은
**headless 만** 검증했다.

- `npm test` **657 passed / 50 files** (신규 `watchNudge` 8 · `배너 배선` 5) · `npm run build` 통과.
- **안 한 것**: 하네스에서 배너의 실제 렌더·줄바꿈·최소폭 확인. **`.ba-wnudge` 는 사람 눈으로 본 적이
  없다.** `flex-wrap: wrap` + `min-width: 0` 으로 넘침이 구조적으로 안 나게 짰지만, **보기 좋은지는
  모른다**(버튼이 아랫줄로 내려가는 모양이 어색할 수 있다). 검증 원장에 `pending` 으로 올렸다.
- 모션 감사: 새 모션은 `.ba-wnudge-go` 의 `filter .15s` + `:active { scale(0.97) }`(기존 찜 행 버튼과
  **같은 관용구**)와 `.ba-wnudge-x` 의 색 전환뿐. `transition: all`·`ease-in`·`scale(0)`·레이아웃 속성
  애니메이션 없음. **배너 등장에는 애니메이션을 넣지 않았다** — 거래소는 페이지 이동이 잦아 등장 모션이
  고빈도가 된다.

## 찜 시세 일괄 확인 — 스스로 멈추는 순회 (2026-09-05)

제보(2026-09-04) 넷째 항목의 앞쪽(④-a). **뒤쪽(④-b 자동 주기)은 설계만 하고 구현하지 않았다** —
`docs/superpowers/specs/2026-09-05-찜-시세-갱신-간격-design.md` 참조.

### 이 기능은 한 번 뺐던 것이다

2026-08-13 에 지운 그 버튼이다. 그때는 10개씩 묶어 **대기 없이** 쏴서 찜 61개를 넘으면 429 를 맞았고,
그 정지가 **엔드포인트 단위**라 사용자의 실제 거래소 검색까지 멈췄다. 다시 넣는 전제는 셋 —
**순차 · 간격 강제 · 언제든 중단.** 그 전제를 코드로 강제하는 곳이 `src/lib/watchRefresh.js` 다.

### 진짜 병목은 짧은 창이 아니라 긴 창이었다

이번에 설계를 바꾼 지점이다. 짧은 창(계정 6요청/4초)은 기존 `MIN_GAP_MS`(700ms) 간격이 구조적으로
막는다. 막지 못하는 건 **IP 100요청/300초**다 — 700ms 로 100개를 돌면 69초가 걸리는데 그 100요청이
곧 **5분치 예산 전부**이고, 그 예산은 거래소 사이트와 공유한다. 다 태우면 사용자가 검색을 못 한다.

그래서 **고정 상한을 박지 않고 응답 헤더의 남은 예산을 매번 읽는다.**
`longWindowHeadroom()` 이 한도(`x-rate-limit-ip`)와 사용량(`x-rate-limit-ip-state`)을 **같은 기간끼리**
짝지어 빼고, 잔량이 `USER_RESERVE`(30) 이하로 내려가면 남겨 둔 채 멈춘다.
헤더를 못 읽으면 추측하지 않고 `MAX_PER_RUN_UNKNOWN`(40)으로 스스로를 묶는다.

⚠ **40 은 측정값이 아니라 보수적 선택이다** — 문서화된 IP 한도(100/300초)의 절반 아래.

### 한 것

- **`src/lib/watchRefresh.js`(신규)** — `longWindowHeadroom` · `canSendMore` · `runBulkWatchCheck`.
  fetch·시계·잠자기를 전부 주입받아 **테스트가 실시간을 안 기다린다**(25건 유닛).
- **찜 섹션 머리에 '전체 확인'** — 여기서 확인 가능한 찜이 **2개 이상일 때만** 그린다.
  1개면 행의 개별 확인으로 충분하고, 다른 거래소 것뿐이면 눌러도 아무 일이 없다(폴더 비우기와 같은 규칙).
- **도는 동안 `중단 (3/12)`** — 다시 누르면 멈춘다. 별도 중단 버튼을 두지 않은 건 섹션 머리에 자리가 한 칸뿐이라서다.
- **멈춘 이유마다 다른 문구** — `done`·`cancelled`·`budget`·`cap`·`blocked`·`error`.
  이유를 안 알리면 "덜 확인하고 멈췄다"가 고장으로 읽힌다.

### 설계 판단 — 뒤집기 전에 읽을 것

- **창구(`watchGate`)를 개별 확인과 공유한다.** 예전엔 `lastWatchReqAt`·`watchBlockedUntil` 두 모듈
  변수였다. 일괄이 자기 것만 세면 둘이 **함께** 계정 규칙(6요청/4초)을 넘긴다. 겸사겸사
  **일괄이 도는 중엔 개별 확인을 막는다** — 같은 창구를 둘이 동시에 쓰면 간격 계산이 어긋난다.
- **한 건 실패하면 전체를 멈춘다.** 30건 성공 뒤 하나 터졌다고 계속 두드리지 않는다. 결과는 남긴다.
- **진행 중 재렌더를 하지 않는다.** 건마다 다시 그리면 스크롤이 튄다. 진행은 버튼 라벨이 나르고,
  행은 끝난 뒤 한 번에 갱신한다. 버튼이 재렌더로 갈릴 수 있어 `btn.isConnected` 로만 그린다.
- **`WATCH_CAP` 주석이 낡아 있었다** — "10개씩 배치 → 최대 10요청" 은 2026-08-13 에 사라진 방식이다.
  지금 상한의 이유는 저장 용량과 화면이라고 고쳐 적었다.

### 검증

- `npm test` **644 passed / 50 files** (신규 `watchRefresh` 25 · `watchBulk.dom` 11) · `npm run build` 통과.
- 하네스 실측(최악 폰트 강제, 최소폭 384):
  - 찜 섹션 머리 **필요 222 / 가용 342 → 여유 120px**, `nowrap` 1줄(높이 36). 이 머리는
    `.ba-list-head` 밖이라 m 밴드 병합과 무관하다.
  - 정상 순회: 같은 거래소 2건만 조회(`L1`·`L2`), 다른 거래소 `L3` 는 **안 부름** ·
    진행 `중단 (1/2)` · 끝나면 라벨 원복 · 행이 '있음' 으로 갱신 · 토스트 정확.
  - **예산 부족**(300초 창 71/100 → 잔량 29): 1건만 보내고 멈춤 +
    *"거래소를 계속 쓰실 수 있게 요청 여유를 남기고 멈췄어요"*.
  - **429**(`retry-after: 7`): 맞은 뒤 한 건도 더 안 보냄 + *"7초 뒤에 이어서 확인해 주세요"*.
- ⏳ **실제 거래소 미검증** — 하네스 fetch 는 스텁이다. 특히 **실제 응답 헤더가 정말 이 형식인지**는
  라이브에서 한 번 봐야 한다(형식이 다르면 `known:false` 로 떨어져 40건 상한으로만 동작한다 — 안전 쪽 실패다).

### 하네스 함정 하나 더 (2026-09-05, 새 워크트리에서)

**`preview_start` 는 세션의 launch 디렉토리를 cwd 로 vite 를 돌린다.** `EnterWorktree` 로 새
워크트리에 들어가도 하네스는 **옛 워크트리 코드를 서빙한다.** `--config` 에 새 워크트리의 절대경로를
줘도 소용없다 — `vite.harness.config.js` 의 `root: 'test-harness'` 가 **cwd 기준**으로 풀리기 때문이다.
- 증상: 새로 넣은 CSS 클래스가 그림자 스타일시트에 **없다**(`css.includes('.ba-wcheck-all') === false`).
  이걸 못 알아채면 "왜 버튼이 안 뜨지" 로 한참 헤맨다.
- 해결: **root 를 절대경로로 박은 설정 파일을 저장소 밖(스크래치패드)에 만들고** launch 디렉토리의
  `.claude/launch.json` 이 그걸 가리키게 한 뒤, **검증이 끝나면 되돌린다.**
  (되돌리지 않으면 그 워크트리가 dirty 라 자동 정리가 영구히 막힌다.)

## 패널 화면 정리 — 섹션 순서·접기 + 상단 간결 + 가져오기 진행 표시 (2026-09-04)

**제보** (커뮤니티, `v0.12.0` 의 일괄 삭제·교체 가져오기를 요청했던 **같은 사람**):
① 파일 불러오기·목록 갱신에 딜레이가 있는데 안내가 없어 "중간에 꼬인다" ② 섹션 순서를 바꾸고
북마크를 통째로 접고 싶다 ③ 상단 타이틀·저장·시세를 내리거나 숨기고 싶다 ④ 찜 시세 일괄 조회·
갱신 간격. **동기는 하나다 — 시즌 끝물이라 북마크보다 찜을 더 자주 본다.**

**사용자 결정**: ①②③ 만 이번에. ④는 후속(아래 「미완료」).

### 한 것

- **섹션 순서** — `src/lib/secOrder.js`(신규, 순수) + `renderList` 를 조각 3개로 분해.
  `html +=` 로 이어붙이던 것을 `parts.bookmarks/watch/history` 로 나눠 `secOrder.map(...).join('')`.
  설정 모달에 `data-setting="secorder"` ▲▼ 목록(6가지 순열 전부).
- **섹션 접기** — 세 섹션 제목이 곧 접기 버튼(`.ba-sec-title[data-sec]`). 폴더 헤더와 **같은 언어**
  (chevron 회전 + 본문 `display:none`)라 새로 배울 게 없고, **버튼을 하나도 안 더해** 액션 행 폭
  예산에 영향이 0 이다.
- **상단 간결** — `.ba-root[data-headcompact]` 하나로 브랜드 줄·시세·동향을 접는다.
  설정 `data-setting="header"`(표시/간결). 실측 **목록 +45px**.
- **가져오기 진행 표시** — 버튼을 스피너로 잠그고 "가져오는 중…" 토스트. 잠금은 **모듈 레벨**이다
  (진행 중 재렌더가 버튼 DOM 을 바꾸므로 버튼에 들려 두면 그 순간 풀린다).

### 설계 판단 — 다음 세션이 뒤집기 전에 읽을 것

- **북마크를 접어도 검색행은 남긴다.** 그 검색창은 북마크와 히스토리를 **동시에** 훑는다
  (`applyFilters`). 같이 접으면 히스토리를 찾을 방법이 없어진다. 그래서 검색행만 `.ba-sec-body`
  밖(`.ba-list-head` 안)에 둔다. 액션 행은 본문 안이라 같이 접힌다.
- **접혀도 헤더와 개수는 남긴다** — 개수가 사라지면 '없어졌다'로 읽힌다.
- **순서 ▲▼ 를 설정 안에 뒀다.** 섹션 머리는 m 밴드(500px↑)부터 검색창·정렬과 **한 줄로 합쳐지는데**,
  거기에 버튼 2개를 더하면 그 줄이 깨진다(액션 행이 같은 이유로 3번 깨졌다). 최악 폰트 실측 결과
  chevron 이 제목을 19px 넓혀 **여유가 37 → 18px** 로 줄었다 — 버튼까지 넣을 자리는 없었다.
- **`uiSecOrder` 는 읽을 때마다 정규화한다**(`normalizeSecOrder`). 모르는 키는 버리고 빠진 키는
  뒤에 채운다. 안 하면 섹션이 늘거나 줄 때 **그 섹션이 화면에서 통째로 사라지는데**, 사용자에겐
  '북마크가 없어졌다'로 보인다.
- **⌨ 단축키 칩은 숨기지 않고 옮긴다.** 단축키 목록이 그 팝오버에만 있어서 숨기면 Alt+S·Alt+K 를
  볼 곳이 아예 없어진다. 간결 모드에서 `.ba-econ-row` 로 **요소를 이동**시킨다(마크업은 한 벌 —
  복제하면 반드시 갈라진다). 팝오버는 `mouseenter` 에서 칩 rect 로 위치를 잡으므로 옮겨도 그대로 뜬다.
- **'현재 검색 저장'은 남긴다.** Alt+S 가 있지만 그걸 모르는 사용자에겐 핵심 기능이 통째로 사라진 것이 된다.
- **`headCompact` 는 localStorage 거울(`baPanelLayout`)에도 쓴다** — `brief` 와 같은 이유로,
  storage 응답을 기다렸다 켜면 브랜드 줄이 잠깐 보였다 사라지는 게 눈에 띈다.

### 같이 드러난 기존 결함 — 찜만 있는 사용자는 자기 찜을 못 봤다

빈 상태 분기(`bookmarks.length===0 && folders.length===0 && history.length===0`)의 **`else` 안에
찜·히스토리 렌더가 통째로 들어 있었다.** 북마크·폴더·히스토리가 없고 찜만 있으면 마스코트 안내만
뜨고 **찜 섹션이 아예 안 그려졌다.** 섹션을 조각으로 나누면서 그 결합이 자연히 풀렸다 — 이제 각
섹션이 자기 데이터만 보고 자기 몫을 그린다. 회귀 테스트로 고정했다.

### ① '목록 갱신 스피너'는 만들지 않았다 — 재보니 필요 없었다

| 데이터 | jsdom (vitest) | **실제 크로미움 (하네스)** |
|---|---|---|
| 북마크 200 + 히스토리 300 | 440~670ms | **37~45ms** (4런) |
| 북마크 400 | — | 63~93ms (3런) |
| 북마크 800 | — | 121~173ms (3런) |

**jsdom 값을 근거로 삼았으면 있지도 않은 문제에 스피너를 달 뻔했다** — innerHTML 파싱이 느려
실제의 12배로 나온다. 실제 브라우저에선 800개에서도 못 느끼는 구간이라, 표시를 붙이면 도움이
아니라 깜빡임만 는다.

그러면 제보자가 느낀 딜레이는 **가져오기 파이프라인**이다(파일 대화상자 → 읽기 → 파싱 → 백업
내려받기 → `chrome.storage.local` 쓰기). ⚠ **하네스의 목 storage 는 인메모리 Map 이라 저장 지연이
재현되지 않는다** — 실제 확장의 storage 쓰기 지연은 여기서 잴 수 없다. 위 잠금·진행 표시가 정확히
그 구간을 덮는다.

### 설계 판단 — '자동 미리보기'를 안 만든 이유

`.ba-tour-spot` 이 `pointer-events: none` 이라 **투어가 떠 있는 채로 밑의 세그먼트가 그대로 눌린다.** 눌린 값은 바로 적용·저장된다. 그래서 값을 임시로 적용했다 되돌리는 장치가 통째로 필요 없고, **복원 실패로 설정이 바뀐 채 남을 위험도 없다.** 카드의 `.ba-tour-try`("지금 눌러도 바로 적용돼요")가 이 사실을 알린다 — 이 줄이 없으면 화면만 봐서는 알 수 없다.

같은 이유로 **자동 시작이 방해가 되지 않는다**: 첫 스텝이 '패널 위치'라 그것 때문에 급히 연 사람은 그 자리에서 목적을 달성한다.

- **투어 카드가 `right: 420px` 고정이었다** — 최소폭(384) 시절 값이라 폭을 넓힌 사용자에게는 **카드가 패널 위에 겹쳤다.** 설정 모달이 패널 안이라 둘러보기에서 크게 드러난다. `panelW + 36` 으로 파생시키고 화면 밖으로 안 나가게 클램프했다. 메인 투어에도 같이 적용된다.

### 마크업 계약

설정 항목을 `.ba-setting[data-setting="side|open|width|brief|fuzzy"]` 로 감쌌다 — 라벨+세그먼트+힌트가 **한 덩어리**여야 스포트라이트가 항목 전체를 비춘다. `.ba-setting` 은 `.ba-folder-pick` 의 flex 규칙을 그대로 복제해 **여백이 감싸기 전과 같다**(하네스 실측: 항목 안·항목 사이 모두 6px 그대로). 기존 클릭 핸들러는 후손 선택자라 그대로 동작한다.

### 기존 사용자 알림 — `WHATS_NEW_VERSION` `0.9.0` → `0.13.0` (2026-09-03, 사용자 요청)

이미 투어를 본 사용자(`tourDone`)는 스텝을 고쳐도 영영 안 본다. `whatsNewSeen !== WHATS_NEW_VERSION` 일 때 **그 버전이 적힌 스텝만** 한 번 보여주는 기존 장치를 썼다.

- ⚙ 스텝의 `since` 를 `'0.13.0'` 으로 함께 올렸다. **상수만 올리면 `TOUR.filter(s => s.since === WHATS_NEW_VERSION)` 가 빈 배열이라 아무것도 안 뜨고 표시만 조용히 찍힌다** — 에러도 안 난다. 이 조용한 실패를 테스트로 막았다(회귀 확인: 상수를 `9.9.9` 로 바꾸면 그 테스트가 실패한다).
- 옛 `since: '0.9.0'` 세 개는 그대로 뒀다 — 이제 안 뽑히지만 '언제 들어온 스텝인가'의 기록이다.
- 소식은 **1스텝**이다. 갈래('하나씩 볼게요')를 누르면 그 자리에서 6스텝이 된다. 안 누르면 `settingsTourSeen` 이 안 찍혀 ⚙ 점이 남고, 나중에 설정을 열 때 자동 시작이 걸린다(의도한 동작).
- 실측(하네스): `whatsNewSeen:'0.9.0'` 상태로 마운트 → 1.2초 뒤 `새로워진 기능 · 1 / 1` + 설정 모달이 실제로 열림 → 갈래 → `2/6`~`6/6` → 종료 시 **투어가 연 모달은 닫히고** 점도 사라짐, `whatsNewSeen:'0.13.0'`·`settingsTourSeen:true`.

⚠ **`manifest.json`·`package.json` 은 아직 `0.12.0` 이다.** 버전 범프는 릴리즈 작업이라 손대지 않았다 — **릴리즈 때 `0.13.0` 으로 올려 이 상수와 맞출 것.** (`WHATS_NEW_VERSION` 은 매니페스트를 읽지 않고 `whatsNewSeen` 키하고만 비교하므로 동작 자체는 어긋나도 되지만, 어긋난 채 나가면 다음 사람이 헷갈린다.)

## 거절 결정 — 패널에 Google AdSense (2026-08-31)

|---|---|

| **Chrome 웹스토어 단일 목적 정책** | 광고 주입은 **그것이 확장의 유일한 목적일 때만** 허용된다. 정책 FAQ 취지: 다른 기능이 있으면 "광고 주입을 멈추든지, 광고 주입 외의 모든 기능을 없애든지". 우리는 북마크·히스토리 도구라 자동 위반 |
| **MV3 · CSP** (정책이 없어도 막힘) | `adsbygoogle.js` 원격 로드가 필수인데, 팝업은 확장 CSP `script-src 'self'` 가 막고 MV3 에서 원격 호스트로 완화할 수 없다. 패널은 Shadow DOM(`panel.js:32` `attachShadow`) 안이라 거기 넣은 스크립트는 **거래소 페이지 CSP** 를 따른다 |
| **사이트 등록 불가** | AdSense 는 계정에 등록·승인된 도메인에만 서빙한다. `poe.kakaogames.com`·`www.pathofexile.com` 은 우리 소유가 아니라 등록 자체가 성립하지 않는다 |

**우회로 보이는 것도 같은 벽이다** — 팝업에 `seominugi.com` iframe 을 띄워 그 안에서 서빙하는 방식은 "소프트웨어 애플리케이션에 통합" 그 자체라 AdSense 계정 정지 사유이고, 스토어 심사에서도 걸린다.

### 이미 있는 것 — 절반은 만들어져 있다

이게 함정이다. "거의 다 돼 있는데?" 로 보여서 다시 파게 된다. 비싼 건 이 부분이 아니다.

| 필요한 것 | 현재 |
|---|---|
| 결과 행 식별 | `.row[data-id]` (`content-main.js`) |
| **행별 가격** | `pobPrices` 맵 `result.id → {amount, currency}` — page-bridge 응답 훅으로 이미 흐른다 |
| 통화 환산 | `baseFromPrice`·`divineFromPrice` + 환율 캐시 |
| DOM 변화 감시 | MutationObserver 이미 사용 중 |
| 라이브 켜기·성공 판정 | `autoStartLive` (라벨 변화로 확인) |

**가격 조건 필터는 새로 만들 게 사실상 없다.** 비싼 건 "새 매물이 떴다"를 **어디서 아느냐**다.

### 검토한 방식과 기각 사유

| | 방식 | 기각 사유 |
|---|---|---|
| ① | 탭 제목·파비콘·확장 아이콘 배지 | **무의미.** 사용자는 브라우저가 아니라 **게임 안에** 있다. 탭 스트립은 안 보이는 자리다 |
| ② | 탭 유지 + OS 알림·소리 | 알림 권한 → 전체 사용자 재승인. 북마크 N개 = 탭 N개 |
| ⑤ | 페이지 컨텍스트에서 WS 다중 연결 (한 탭) | SW 수명 문제는 사라지나 **계정 리스크**가 남는다. 인증·동시 상한 **미검증** |
| ③ | 서비스 워커가 자체 WS (탭 0개) | 위 + **MV3 SW 는 메시지 30초 없으면 죽는다** → 조용히 감시 정지 |

**어떤 방식이든 공통으로 걸리는 것**
- 알림 채널 자체가 불확실하다 — **전체 화면 게임에서는 윈도우가 알림을 억제**한다(집중 지원). 완벽히 만들어도 안 닿을 수 있다. 닿는 채널은 오히려 **소리**다.
- 우리 설계 원칙 ⑧ **"우리는 WebSocket 을 만들지 않는다"** 를 정면으로 뒤집는다. 인증·재연결·GGG 동시 연결 정책이 전부 거래소 쪽에 있어서 지금까지 새 권한 0 으로 버텼다.

### 되짚을 조건 — 이때 다시 본다

- **0.11.0 배포 후에도 같은 피드백이 오는가.** 이 요청은 **발견 실패**일 수 있다 — `라이브로 열기`가 그동안 `⋯` 메뉴와 Shift+클릭에만 있었다. 0.11.0 에서 **카드 위 버튼(▶)으로 꺼냈다.** 그 뒤 피드백이 줄면 기능 부재가 아니었던 것이다.
- 불만이 "알림이 없다" 가 아니라 **"탭이 많아진다"** 로 확인되면, 알림 없이 **다중 선택 → 한 번에 라이브 탭 열기**만 주는 값싼 대체가 있다(기존 `#ba-live` 경로 재사용, 새 권한 0, 백그라운드 0). 그건 수용 기준에 걸리지 않는다.

### 내보내기가 오래된 북마크를 빼던 문제 — 교체와 만나면 영구 소실 (2026-08-25, 브랜치 `claude/json-bookmark-deletion-e31755`)

### 결과 행 버튼(★·PoB)이 스탯 위에 겹쳐 뜨던 문제 (2026-08-25, 브랜치 `fix/demand-badge-icon-position`)

**제보(커뮤니티)**: "수요가 있는 아이템에는 찜하기와 영문복사 아이콘이 우측에 표기되는 버그가 있어요."

**원인**: 버튼 자리 찾기 1순위가 **상태 배지의 텍스트**(`/인증/`)를 앵커로 썼다. 그런데 그 배지
(`.verifiedStatus`)는 매물 상태에 따라 **문구가 바뀐다** — `수요가 있는 아이템입니다` 가 뜨면 앵커를
못 찾아 2순위(절대 위치, 이미지 오른쪽)로 떨어지고, 거기가 비어 있지 않아 **아이템 스탯 위에 겹쳤다.**

**⚠ 같은 원인으로 영문 거래소에서는 1순위가 한 번도 잡힌 적이 없다** — 거긴 `Verified` 라서. GGG 계정
사용자는 그동안 계속 2·3순위로 떨어져 있었다는 뜻이다.

**고친 것**: 앵커를 텍스트에서 **클래스(`.iconContainer`)** 로 바꿨다. 문구·언어·인증 여부와 무관해진다.
삽입은 그 컬럼에 `appendChild` — 정상 행에서 `.ba-pob-wrap` 이 이미 그 컬럼의 마지막 자식이라
**결과 DOM 이 기존과 동일**하다.

**실측한 DOM 계약 (2026-08-25, 카카오 poe1·poe2 both · 각 10/10행)** — 다음에 이 자리를 만질 때의 근거:

<div class="row" data-id="…">

    <div class="verifiedStatus">인증 완료</div>   ← 문구가 바뀌는 자리. 텍스트로 잡지 말 것
    <div class="ba-pob-wrap">…★ · PoB…</div>      ← 우리가 붙이는 자리
  </div>

### 동기화 — 다음에 이 주제가 오면 (2026-08-24 조사, 미착수)

교체 모드는 "한쪽이 정본" 모델이라 손 동기화를 덜 아프게 할 뿐 **동기화가 아니다.** 진짜로 하려면 순서가 있다.

**전송 수단이 아니라 데이터 모델이 먼저 막는다.** 지금은 ① 두 기기에서 같은 북마크를 알아볼 안정 키가 없고
(id 는 기기별 발급, `dedupeKey` 는 조건을 고치면 바뀐다) ② **"지웠다"는 사실이 안 남아** 삭제가 전파될 수 없고
③ 마지막 동기화 시점(base)이 없어 어느 쪽이 바뀐 건지 판정할 수 없다. `chrome.storage.sync` 를 붙여도
**②는 그대로**라 자동으로 지저분해질 뿐이다.

2단계로 `syncId`(불변) · `deletedAt` 툼스톤 · `lastSyncAt` 을 넣으면(스키마 v4) **파일 한 개로도 3-way 병합**이
된다 — base ↔ 내 현재 ↔ 상대 파일. 그게 끝나면 전송 수단은 갈아끼우기 자유다.

| | 크롬 계정 sync | 파일(지금) | 파일 + 핸들 기억 | 자체 서버 |
|---|---|---|---|---|
| 공용 PC | ✗ 로그인 불가 | ✓ | ✓ | ✓ |
| 손이 가는 정도 | 없음 | 클릭 2회 + 탐색기 | 클릭 1회 | 없음 |
| 용량 | **제한**(아래) | 무제한 | 무제한 | 무제한 |
| 새 권한 | 없음 | 없음 | 없음 | **전체 재승인** |

- **`chrome.storage.sync` 용량이 생각보다 빡빡하다**: 문서상 총 102,400B · 항목당 8,192B · 512항목인데
  `sanitizeQuery` 가 조건을 **20,000자까지** 통과시킨다 — **북마크 하나가 항목당 한도를 혼자 넘을 수 있다.**
  총량 쪽(레코드당 ~1KB 추정 → 100개 근처)은 **재보지 않은 추정이다.** 넘으면 조용히 실패 = 「기능 수용 기준」의
  *조용히 죽는 실패*.
- **공용 PC 답은 "전송 수단을 하나로 고르지 않는 것"** — 병합이 전송과 분리돼 있으면 회사는 파일, 집은 계정
  sync 를 섞어 써도 같은 규칙으로 수렴한다.
- 클라우드 드라이브 동기화 폴더에 JSON 하나를 두는 방식은 **전송을 OneDrive/Drive 가 대신해 준다** — 우리가
  만들 게 없다. 회사 PC 에서 그게 되면 사실상 자동이다.
- **File System Access(핸들 기억)는 미검증이다** — 콘텐츠 스크립트에서 `showSaveFilePicker` 가 되는지, 핸들 권한이
  세션 간 유지되는지, 핸들이 페이지 origin 별(카카오/GGG 따로)인지 전부 실측이 필요하다. 추측으로 설계하지 말 것.
