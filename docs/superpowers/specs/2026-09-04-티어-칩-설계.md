# 능력치 필터 티어 칩 (PoE2) — 설계 문서

- **작성일**: 2026-09-04
- **상태**: 설계 승인됨, 구현 전
- **범위**: PoE2 (`trade2`) 전용. PoE1은 이 설계를 재사용하되 별도 작업
- **동기**: 사용자 피드백 — *"화염 피해 #~# 추가나 저항/생명력 등 t1 수치를 넣을 때마다 db 가서 t1 최소/최대 숫자 보고 입력하는 부분이 제일 귀찮다. 클릭 한 번에 t1/t2 넣을 수 있으면 좋겠다"*

---

## 1. 배경 & 목적

거래소에서 능력치 필터에 수치를 넣으려면 사용자가 **사이트를 떠나** 외부 DB에서 해당 부위의 T1 최소/최대를 찾아보고 손으로 입력한다. 이 왕복을 없앤다.

능력치 필터 행 옆에 **티어 칩**을 붙이고, 누르면 그 티어의 최소 수치가 `min` 입력칸에 들어간다.

**핵심 제약**: T1 수치는 **부위마다 다르고**(생명력 최대치 T1 — 반지 `100~119` vs 갑옷 `200~214`), **아이템 레벨 상한에 따라 도달 불가**할 수 있다. 그래서 고정 표를 보여주는 게 아니라 **현재 검색 조건을 읽어** 값을 정한다.

---

## 2. 스코프

### 포함
- 빌드 시점 티어 표 생성 스크립트 + 산출물(`statTiers.poe2.json`)
- 능력치 필터 행에 티어 칩 주입 (도달 가능한 상위 세 티어)
- 칩 클릭 → `min` 입력
- 부위·아이템 레벨을 현재 검색 조건에서 읽어 티어 재계산
- 해당 부위에 그 능력치가 없으면 칩을 띄우지 않음
- 부위 미확정 시 부위 선택 요구

### 제외
- **검색 팔레트** — 별도 후속 작업. 이 칩 위에 얹는다
- **PoE1** — 데이터·매칭률 모두 확인해 두었으나(§6) 이번 범위 아님
- 검색 재생성(POST) 경로 — 칩은 DOM만 만진다
- `max` 자동 입력 — T1의 상한을 넣으면 그 티어 안에서도 최고 굴림만 남아 결과가 과도하게 줄어든다
- 유니크·타락·에센스 등 `normal` 외 버킷

## 3. 사용자 흐름

1. 사용자가 거래소에서 유형(예: 반지)을 고르고 능력치 필터를 추가한다
2. 필터 행 오른쪽에 **도달 가능한 상위 세 티어** 칩이 나타난다 (보통 `T1 T2 T3`, 아이템 레벨 상한이 걸리면 `T3 T4 T5`처럼 내려간다)
3. `T1`을 누르면 `min`에 그 티어의 최소값이 들어간다
4. 아이템 레벨 상한이 걸려 있으면 도달 불가 티어는 칩에서 빠진다 — 결과가 0건이 되는 값을 넣지 않기 위해서다

**부위를 모를 때**: 칩 자리에 `부위?` 를 띄우고, 누르면 부위 목록을 보여준다. 고르면 거래소의 유형 필터도 함께 채운다.

## 4. 아키텍처

프로젝트 CLAUDE.md의 FE 계층(§24)에 맞춘다.

### 4.1 빌드 시점 (개발자 컴퓨터, 게임 패치마다 1회)

```
poe-game-data/poe2/modifiers/json/*.json   (12MB, 34파일)
        │
        │  scripts/build-tier-table.mjs
        │   ├ resolveLockedGameDataRoot() 로 lock 된 스냅샷만 읽는다 (기존 헬퍼 재사용)
        │   ├ 거래소 /api/trade2/data/stats 의 '비고정' 그룹과 문구 대조
        │   ├ 필요 아이템 레벨 내림차순 → T1..Tn
        │   ├ 부위 대응표(31행) 검증 — 누락이면 빌드 실패
        │   └ §5.2a 의 셋을 걸러낸다 (후보 다중 수용 · 값 충돌 계열 폐기 · 배율 미적용 제외)
        ▼
src/lib/statTiers.poe2.json   (gzip 11.6KB, 32부위 688스탯)
```

산출물은 **저장소에 커밋**한다. `pobBaseMap.json`과 같은 취급이다 — 실행 시점에 네트워크를 타지 않으므로 **새 권한이 필요 없고, 기존 사용자 재승인도 없다**(프로젝트 CLAUDE.md 기능 수용 기준 4항).

### 4.2 실행 시점 (사용자 브라우저)

| 계층 | 파일 | 역할 |
|---|---|---|
| Domain Core | `src/lib/statTiers.js` (신규) | 순수 조회 — `(부위, statId, ilvl상한) → 티어 목록`. 부위 미상·능력치 없음을 명시적으로 구분해 반환 |
| Domain Core | `src/lib/itemClass.js` (신규) | 베이스명·category 옵션 → 부위. `pobBaseMap.json` + category 대응표 |
| Presentation | `src/content/tier-chip.js` (신규) | 칩 렌더·부착·클릭 처리 |
| Presentation | `src/content/content-main.js` (수정) | 기존 `MutationObserver`에 칩 부착 훅 추가 |

`content-main.js`가 `tier-chip.js`를 import 한다 — **`manifest.json`은 건드리지 않는다**(vite가 번들한다).

### 4.3 검색 조건 읽기 — 3단 폴백

| 순위 | 출처 | 비고 |
|---|---|---|
| 1 | `page-bridge`가 캡처한 최근 검색 query | 한 번이라도 검색했으면 가장 정확. 이미 있는 경로 |
| 2 | 거래소 화면 직접 읽기 | 검색 전 상태용. GGG가 화면을 바꾸면 깨지므로 실패를 전제로 감싼다 |
| 3 | 사용자에게 부위를 물음 | 위 둘이 모두 비었을 때 |

query에서 읽는 자리 — **PoE1과 다르므로 주의**:
- 부위: `query.filters.type_filters.filters.category.option` (예: `accessory.ring`)
- 베이스명: `query.type` → `pobBaseMap.json` → 부위
- 아이템 레벨: **`query.filters.type_filters.filters.ilvl`** (PoE1은 `misc_filters.ilvl`)

### 4.4 값 입력 — 3단 폴백

`fuzzyPrefix.js`가 기록한 대로 거래소 입력칸은 Vue가 제어한다. 능력치 **이름** 칸(vue-multiselect)은 네이티브 setter가 되돌려지지만 **숫자 칸은 미확인**이다. 실패를 전제로 설계한다.

1. 네이티브 value setter + `input`·`change` 이벤트 → **읽어서 값이 남았는지 확인**
2. 실패 시 `focus()` + `document.execCommand('insertText')` — 칩 클릭이 user activation을 주므로 이 창 안에서는 동작한다(`fuzzyPrefix.js`가 쓰는 경로)
3. 그래도 실패 시 **값을 넣지 않고 보여준다** — 칩이 수치를 표시하고 클릭 시 클립보드에 복사

3번까지 떨어져도 "DB를 보러 나가지 않아도 된다"는 핵심 가치는 남는다.

### 4.5 거래소 행 마크업 — 실측 (2026-09-04)

계획 단계에서는 못 봤다(한국 IP 리다이렉트). 사용자 크롬에 **이미 로그인 세션이 있어서**
Claude in Chrome 으로 확인했다 — API 경로로 로그인 상태를 먼저 확인해 로그인 페이지를
거치지 않는 것을 보장한 뒤 들어갔다.

```html
<span class="filter-body">
  <div class="filter-title filter-title-clickable">
    <i class="mutate-type mutate-type-explicit">비고정</i>   <!-- 그룹 배지 -->
    <span>화염 저항 #%</span>                                 <!-- 진짜 능력치 이름 -->
  </div>
  <span class="sep"></span>
  <input type="number" placeholder="최소" class="form-control minmax">
  <span class="sep"></span>
  <input type="number" placeholder="최대" class="form-control minmax">
</span>
```

**확인된 것**

- 행 찾기 규칙(최소 칸 → 위로 올라가며 텍스트 있는 조상)이 **그대로 통한다** —
  min 칸 39개가 전부 **깊이 0**(바로 위 부모가 행)에서 잡혔고, 컨테이너 가드에 막힌 것 0
- `최소` placeholder 는 능력치 행만 쓰는 게 아니다 — 39개 중 **능력치 행은 2개**이고
  나머지는 아이템 레벨·퀄리티·피해·DPS 등이다. 의도대로 그 37개에는 아무것도 안 붙는다
- 값도 맞다: 반지 `화염 저항` T1(41) T2(36) T3(31) · `생명력 최대치` T1(100)

**여기서 잡은 결함** — `<i>` 배지를 빼지 않으면 행 텍스트가 `"비고정 화염 저항 #%"` 가 되어
거래소 스탯 목록(`"화염 저항 #%"`)과 **한 건도 안 맞는다.** 라이브 대조 0/2 → 뺀 뒤 2/2.
기능이 통째로 조용히 죽는 경로였고, jsdom 테스트로는 절대 나올 수 없었다.

## 5. 데이터

### 5.1 티어 표 스키마

```jsonc
{
  "Ring": {
    "explicit.stat_3372524247": [        // 화염 저항 #%
      { "t": 1, "l": 82, "v": [[41, 45]] },   // t=티어, l=필요 아이템 레벨, v=값 슬롯별 범위
      { "t": 2, "l": 71, "v": [[36, 40]] }
    ]
  }
}
```

- `v`는 **슬롯 배열**이다. `공격 시 화염 피해 #~# 추가`는 거래소 능력치 한 줄에 슬롯이 둘(`[[25,29],[37,45]]`)이다 — §7 미정 ②
- 키는 거래소 stat id. 부위는 modifiers 파일명

### 5.2 티어 번호

게임 데이터의 `tier` 필드는 **티어가 아니라 필요 아이템 레벨**이다(`AddedFireDamage1`의 `tier: 1`은 최하위). **필요 레벨 내림차순으로 T1부터** 매긴다 — PoE2도 T1이 제일 좋다(사용자 확인, 2026-09-04).

### 5.2a 표를 만들 때 걸러내는 셋 (2026-09-04 구현 중 발견)

계획을 세울 때는 "문구가 맞으면 쓴다"로 충분한 줄 알았는데, 실제로 만들어 보니 셋이 더 필요했다.

**① 후보가 여럿인 문구 — 받아들인다**
같은 정규화 문구에 거래소 stat id가 둘인 경우가 **6종 197건** 있다(생명력·마나 흡수, 모든 능력치,
정신력 둘, 출혈 유발). 거래소 목록 자체의 중복이라 사용자에게는 같은 문구 하나로 보인다.
그래서 **후보 id 전부에 같은 티어 사다리를 단다** — 어느 쪽을 골랐든 보여줄 값은 같다.
한 부위 안에서 계열이 갈리는지 45건을 전수 확인했고 44건이 안전했다.

**② 같은 요구 레벨에 값이 갈리는 계열 — 버린다**
①의 나머지 1건이 여기 걸린다. 특례가 아니라 일반 가드로 둔다: 한 계열 안에서 같은 요구 레벨에
서로 다른 값 범위가 오면 티어 순서를 정할 수 없다. **152개 계열이 걸리는데 전부 주얼이다** —
`JewelArmour`(방어도 10~20% 증가)와 `JewelRadiusArmour`(2~3%)처럼 문구가 같은 별개 모드다.

**③ 표시 배율이 적용되지 않은 스탯 — 제외한다**
`poe-game-data` 추출이 GGPK의 표시 배율을 적용하지 않아 값이 100배·60배로 들어 있다.

| 내부 스탯 | 게임 데이터 표기 | 실제 표시 |
|---|---|---|
| `*_permyriad` (4종) | `물리 피해의 (600-690)%를 흡수` | 6.00~6.90% |
| `local_critical_strike_chance` | `치명타 확률 (101-150)%` | 1.01~1.50% |
| `*_life_regeneration_rate_per_minute` | `1초마다 생명력 (60-120) 재생` | 초당 1~2 |

**이름 규칙만으로는 못 잡는다** — `local_critical_strike_chance`에는 접미사가 없다. 값 크기로도
못 자른다 — `화염 피해 238% 증가`는 정상값이다. 그래서 **내부 stat id 목록으로 못박는다.**

배율(÷100·÷60)을 넣어 되살릴 수 있지만 **게임으로 검증하지 못해 v1에서는 제외**한다
(사용자 결정, 2026-09-04). 무기의 `치명타 확률`이 빠지는 게 가장 큰 손실이다. 게임에서 확인되면
그때 배율을 넣어 되살린다.

### 5.3 문구 정규화 규칙

게임 문구와 거래소 문구를 잇는 규칙. 순서가 중요하다.

1. 괄호 범위 `(30-35)` → 슬롯 표식
2. `a~b` → 슬롯 표식 둘
3. 표식과 `~`로 이어진 상수도 슬롯 (`1~(2-3)` → 슬롯 둘)
4. 표식 수가 그 문장의 **슬롯 개수보다 적으면**, 남은 상수를 왼쪽부터 슬롯으로 승격 (`모든 근접 스킬 레벨 1` → `모든 근접 스킬 레벨 #`)
5. 표식 → `#`, 부호 `+#`/`-#` → `#`, 공백 정리

4번이 없으면 매칭률이 91.0%에 머문다. 슬롯 개수는 `stats[].stats[].length`에서 온다.

### 5.4 부위 대응표 (31행)

`pobBaseMap.json`의 PoB 클래스명 → modifiers 파일명. **자동 단수화는 쓰지 않는다** — `Staves↔Staff`, `Quarterstaves↔Warstaff`, `Foci↔Focus`, `LifeFlask`(구분자 없음)에서 전부 깨진다.

빌드 스크립트가 **양방향 검증**한다: 지목한 modifiers 파일이 없거나 · `pobBaseMap`에 없는 클래스를 지목하거나 · 티어 데이터가 비면 **빌드를 깨뜨린다**.

**알려진 공백** (오류 아님) — 어느 쪽이 비어 있는지가 다르다:

| 공백 | 어느 쪽이 없나 |
|---|---|
| `AbyssJewel` · `Map` · `UtilityFlask` | modifiers 파일은 있는데 PoE2에 **해당 베이스가 없다** |
| `Charms` | 베이스는 있는데 **modifiers 파일이 없다** |
| `Fishing Rods` (`weapon.rod`) | 거래소 category 와 베이스(낚싯대 1종)는 있는데 **modifiers 파일이 없다** |

모두 결과는 같다 — 부위가 `null` 로 판정돼 칩이 뜨지 않는다. GGG가 나중에 모드를 붙이면
`poe-game-data` 스냅샷 갱신 후 대응표에 한 행 추가하면 된다.

## 6. 실측 근거 (2026-09-04)

거래소 응답은 `https://poe.kakaogames.com/api/trade2/data/{stats,filters}` 실측. 게임 데이터는 `poe-game-data v2026.08.30.1`.

⚠ **두 숫자를 구분해야 한다.** 계획 단계에서 이 둘을 섞어 97.0%를 기대치로 적었다가, 구현에서
93.7%가 나와 한 번 멈췄다. 서로 다른 질문에 답하는 값이다.

| 질문 | 값 |
|---|---|
| 대상 모드 (`normal` 버킷, Map 제외) | 5,848 |
| 정규화 문구가 거래소 목록에 **있나** | 5,675 (97.0%) |
| 그중 후보가 **하나로 확정**되나 | 5,478 (93.7%) |
| **최종 — §5.2a 셋을 적용한 뒤 표에 들어간 것** | **5,366 (91.8%)** |

최종 산출물: **32부위 · 688스탯 · gzip 11.6KB**

빠진 것의 내역: 배율 미적용 제외 309 · 문구 자체가 없음 173 · 값 충돌 계열 152개(전부 주얼).

부위별 문구 매칭률(§5.2a 적용 전): 목걸이·허리띠·반지·부적 **100%** · 투구 96.5% · 장갑 96.3% ·
장화 95.6% · 석궁 86.6% · 플라스크 71~82%.

**PoE1과의 차이**: 같은 방법으로 PoE1은 88.7%다. PoE2 거래소가 **`+` 부호를 쓰지 않아**(`화염 저항 #%`) 저항 계열이 깔끔하게 이어지는 반면, PoE1은 `화염 저항 +#%`와 `화염 저항 #%`가 모두 있어 충돌한다.

**남는 미매칭**은 대부분 거래소에 능력치 필터가 없는 항목(로컬 방어 수치 등)이라 칩이 필요 없다.

## 8. 완료 기준 (AC)

### 기능 AC
- 부위 `Ring` + `생명력 최대치 #`에서 T1 칩이 `min`에 **100**을 넣는다
- 부위 `Body_Armour` + 같은 능력치면 T1이 **200**이다 (부위에 따라 값이 바뀐다)
- 부위 `Focus` + `생명력 최대치 #`이면 **칩이 뜨지 않는다** (그 부위에 없는 능력치)
- 부위 `Ring` + `화염 저항 #%`에서 아이템 레벨 상한 65를 걸면 T1(필요 82)·T2(필요 71)가 빠지고 **T3(필요 60, 31~35)이 최상단**이 된다
- 슬롯이 둘인 능력치에는 칩이 뜨지 않는다 (미정 ② 해결 전까지)
- 부위를 모르면 칩 대신 부위 선택을 띄운다

### UI AC
- 칩은 능력치 필터 행 안, `min`/`max` 입력칸 근처에 놓이고 라벨은 티어 번호(`T1`)다
- 터치 대상 44×44px 이상
- 확장의 기존 바이올렛 스타일(`.ba-*`)을 따른다 — **새 클래스는 짓기 전에 `panel.css` 를 grep 한다**(네임스페이스가 평평하다)
- Vue가 화면을 다시 그려도 칩이 되살아난다

### 검증
- `npm test` 통과 · `npm run build` 통과
- `chrome://extensions` 압축해제 로드 후 **'POE 브라우저'에서 실측** — 한국 IP에서는 에이전트가 거래소에 접근할 수 없으므로 이 항목은 사용자 확인이다

## 10. 리스크 & 유지보수

- **게임 패치마다 표를 다시 만들어야 한다.** `poe-game-data` 스냅샷 갱신과 묶인다. 기존 `poeGameDataLock.test.js`가 스냅샷 불일치를 잡는다
- **거래소 문구가 바뀌면 매칭이 떨어진다.** 빌드 스크립트가 매칭률을 출력하고, 임계치(기본 90%) 아래면 빌드를 실패시킨다. 현재 91.8% 이므로 여유가 크지 않다 — 문구가 조금만 바뀌어도 걸린다
- **거래소 화면 구조 변경.** 칩 부착·값 입력은 실패해도 조용히 죽지 않게 하고, 기존 기능(북마크·히스토리)에는 영향이 없어야 한다
- 프로젝트 기능 수용 기준 대조: 백그라운드 상시 동작 없음 · 계정 리스크 없음 · 미문서 엔드포인트 없음(이미 쓰는 `data/stats`) · **새 권한 없음**
